# Silly Bilibili 功能与性能调研

> 调研日期：2026-08-21。范围是当前工作树的实际实现；“建议”不是已实现功能。本文不讨论绕过 Android 权限模型的方案：缓存目录可直接读取时走普通文件访问，受隔离时使用用户主动授权的 Shizuku，SAF 仅作为用户可授权目录的备选。

## 1. 产品定位与成功标准

Silly Bilibili 是“本地 B 站缓存的媒体库”，而不是 B 站在线视频客户端。用户核心链路是：**取得可用目录访问 → 可解释地扫描并维护本地库 → 快速定位内容 → 直接播放/导出 → 持续反映外部删改**。

对于 3,000 条以上缓存，产品成功不应只看“最终能列出来”，还应满足：

| 体验目标 | 可量化验收建议 |
| --- | --- |
| 首屏可用 | 冷启动后首页骨架立即出现，首次 40 条数据库结果在中端真机上尽量低于 300 ms（不包含封面生成）。 |
| 浏览连续 | 列表/宫格以稳定帧率滚动；翻入下一批数据不出现全屏闪烁或回到顶部。 |
| 扫描可信 | 仅当目录完整读取成功且是“完整、未筛选扫描”时，才标记缓存源已消失；导出的 MP4 永不因源缓存消失而删掉。 |
| 播放可靠 | 缓存轨道可在 Shizuku 直读失败时降级到临时副本；滑动目标先展示首帧，再开始播放。 |
| 操作可恢复 | 扫描、转换、状态刷新均有阶段、进度、完成/失败结果与可重试入口；进程重建后能恢复可解释的状态。 |

## 3. 分功能调研与改造建议

### 3.1 目录访问与 Shizuku

**现状。** `VideoScanService.resolveScanAccess()` 以“目录可列出”为直接访问标准，直接访问优先；隔离目录再走 `ShizukuFileHelper`。Shizuku 侧已有 AIDL `ShellService` 与批量读取，避免为每一条元数据单独启动 shell。Shizuku 的官方 API 将 UserService 定义为运行在 shell/root 身份的独立 Binder 服务，适合这种批处理文件元数据工作，但同时明确其 `Context` 并不等同普通应用 Context，因此业务应保持为纯文件/Binder 操作。

**产品设计。**

- 扫描页应把访问状态固定为四种可理解的状态：`直接可读`、`需要授权 Shizuku`、`Shizuku 已连接但目录不存在`、`用户选择的 SAF 目录`；分别给出下一步按钮，而不是只显示“不可访问”。
- 第一次使用采用两步引导：先检查 B 站缓存目录是否存在，再仅在需要时引导 Shizuku。不要要求所有用户配置 Shizuku。
- 每次 UserService 断开时，保留上一次扫描库，禁用“开始扫描”并给出“重新连接/重新授权”动作；不要把断开误报成缓存被删除。

**性能与可靠性。**

- 保持“一个常驻 UserService + 有界批读取”的方向。Binder 返回应限制单批内容与总字节数；当前 48 个 `entry.json` 是合理保守值，但需以真机 trace 调整，而非固定猜测。
- 将 `fileLength`、目录列表和访问能力做短 TTL（如 30–60 秒）缓存，并在扫描开始、失败、Shizuku death 时显式失效；避免首页/封面/播放并发重复跨进程探测。
- 加入 Binder death recipient、操作超时、一次自动重绑和结构化错误码（权限被撤回/服务未启动/文件不存在/远端失败）。当前 UI 可提示异常，但缺少统一的错误分类与遥测。
- 不要用 `MANAGE_EXTERNAL_STORAGE` 作为 Shizuku 的替代路径。Android 的 scoped storage 是系统模型，Android 11+ 对应用专属目录创建与跨应用目录访问有限制；产品应以实际可列出目录的能力检查为准，而非仅检查权限标志。

### 3.2 扫描、增量同步与外部删改

**现状。** 扫描顺序是：校验访问 → 列目录 → 批读 `entry.json` → 预筛选 → 对新增候选文件核验 → `syncCacheDirectory()` 事务合并。完整、无筛选扫描才允许 `markSourcesMissingInDirectory()`，且 `exportedPath != null` 的条目不会被删。这与“删除源缓存不影响导出库”的产品要求一致。

**产品设计。**

- 扫描结果应分开呈现：发现文件夹、解析成功、过滤跳过、文件不完整、历史源已消失、已合并、保存失败。用户能据此判断是 B 站删了缓存、手动删了文件，还是 Shizuku 中断。
- “快速扫描”明确标注为**不核验媒体文件、不会判定源缺失**；默认按钮使用“完整扫描”。
- 增加“仅核对变化”入口：复用目录清单和 last-seen，在大库中优先处理新增/消失的 AV 文件夹；完成后再提供“彻底重新扫描”。
- 扫描作业完成后显示可点击摘要（例如“新增 12、更新 28、源已删除 3、失败 1”），离开页面后仍可回看；当前 `ScanJobRegistry` 已具备持有会话状态的基础。

**性能与可靠性。**

- 当前为 `entry.json` 批读取、并发度 4、批量事务，这是正确的第一层优化。重点风险不是解析 JSON，而是跨 Binder 的目录/文件调用次数和全量文件 `stat`。
- 进一步将扫描改为“清单阶段 + 差异阶段”：持久化 AV/CID 目录签名（路径、mtime、entry.json 长度/mtime），签名不变时不重读 JSON、不重做 media stat。注意：只有目录列表确认完整时才执行删除对账。
- 为作业加入取消令牌、暂停点和持久化 checkpoint；目前转换的 `cancelAll()` 是空实现，扫描/转换都需要“用户取消”与“系统杀进程”后可解释恢复。
- 大批插入/更新继续使用单事务，但将数据库写入拆为可控块（如 200–500）并测量 WAL/锁等待；不要在主线程收集每个阶段的细粒度事件。
- 建立至少三组真机基准：500/3,000/10,000 目录，直读与 Shizuku 各一组，记录总时长、Binder 调用数、每阶段耗时、峰值内存和失败率。

### 3.3 多视频卡片展示、搜索、筛选与分类

**现状。** 首页采用 `LazyColumn`/`LazyVerticalGrid`，视频 id 作为 stable key，`contentType` 已区分卡片；首页一批 40，`snapshotFlow` 靠近末尾时预取下一批。分类列表一批 20。数据库搜索与统一筛选用 `LIMIT/OFFSET`。Compose 官方建议为 lazy item 提供稳定 key 和 `contentType`，当前已落实。

**产品设计。**

- 3,000+ 视频首页应采用“摘要密度优先”：一行只保留封面、标题两行、UP/时长/大小、状态，分类/画质作为短标签；点击进入信息面板，避免每卡展示所有字段。
- 在筛选区显示结果总数、活跃筛选数量与“一键清除”；搜索输入防抖 200–300 ms，输入中保留旧结果与轻量 loading，而不是清空列表。
- 提供排序（最近扫描、最近播放、最长、最大、标题）与“仅本地源/仅已导出/两者都有”，这比继续堆叠更多 chip 更利于大库定位。
- 多选跨页必须在操作栏中明确“已选择当前筛选下 N 项”，并对转换/删除二次确认；导出库删除显示会影响的实际文件数量和不可恢复说明。

**性能与可靠性。**

- 当前 `LIKE '%query%'`、动态 `CASE` 方向过滤、`ORDER BY addedAt` 缺少服务于主查询的复合索引。3,000 条通常可用，但 10,000+ 与连续模糊搜索会退化。第一优先级是给 `sourceAvailable, addedAt DESC`、`categoryId, sourceAvailable, addedAt DESC` 建索引，并以 `EXPLAIN QUERY PLAN` 验证。
- 标题/UP/AV 的任意子串搜索不适合普通 B-tree；数据规模上来后采用 Room FTS（FTS4/FTS5）并维护与 videos 的 id 对应表。检索结果先得到 id 页，再回表取卡片字段。Room 官方 DAO 支持 Paging 返回类型；可选从手工 offset 迁移至 Paging 3，使无效化、加载态、末页与恢复滚动位置由库统一处理。
- `OFFSET` 越大跳过越多数据。若仍保留手工分页，改为 keyset/cursor 分页（`addedAt < lastAddedAt`，加 `id` 作为稳定并列键）可避免深页扫描和数据变动导致重复/漏项。
- 封面、线上状态、完整性绝不能直接在 item composition 中启动。维持 ViewModel 的去重/信号量策略，并引入 viewport-aware 请求队列：只给可视区及前后 1–2 屏提交低优先级封面任务；滑离后取消尚未开始的任务。
- 页面状态不应持有无限增长的 `List<Video>`。即使 Compose 只组合可见行，ViewModel 仍会持有已加载数据；Paging 或“窗口缓存 + 当前位置锚点”更适合 10,000+ 条。

### 3.4 封面与首帧预览

**现状。** `CoverCacheService` 的策略正确：已缓存封面 → 真实文件名候选 → 任意图片 → 视频首帧；Shizuku 场景先复制 16 MiB 文件头抽帧，失败再整文件复制；缓存名带视频 id/cid，能避免历史串封面。

**产品设计。**

- 卡片先立即显示固定比例的中性色占位，再交叉淡入封面；失败时显示“重试”而不是永久黑块。
- 封面来源可在详情中标识“缓存封面/视频首帧”，方便排查看似错误但其实是第一帧较黑的情况。
- 不把竖屏封面硬裁成横屏：列表固定框可 `ContentScale.Crop`，但竖屏使用专用 3:4 预览或在宫格中保留比例；当前模型已有 `previewAspectRatio`。

**性能与可靠性。**

- 将封面请求去重键设为 `videoId + source signature`；源封面/视频 mtime 或大小变化才重建。纯“每次进入 app 仅一次”不足以覆盖外部改封面。
- 首帧抽取限并发（建议 1–2），优先可视区；对失败做指数退避，避免滚动时反复复制大 m4s。
- Coil 内存缓存使用低分辨率缩略图，磁盘封面尺寸限制在显示像素的约 2 倍；明确 cache 上限及 LRU 清理，防止封面缓存挤占应用缓存并被系统随机清理。
- 长期可将读取的局部范围交给统一 `DataSource`/缓存层，避免封面、滑动预读、播放各自复制同一份文件头。

### 3.5 缓存与导出视频播放

**现状。** `PlaybackService` 把 ExoPlayer 和 MediaSession 放在 `MediaSessionService`，设置了 10–30 秒常规缓冲；缓存视频使用自定义 `ShizukuDataSource` 和 256 KiB LRU 预读块，跨块请求直接读完整范围以避免误报损坏；失败时 `PlaybackMediaResolver` 可退到应用临时副本。导出 MP4 则走普通文件 I/O。播放页退出会先解绑 Surface 后再导航，防止旧帧残留。

**产品设计。**

- 统一定义播放状态：准备中、首帧已出、播放、缓冲、暂停、文件失效、兼容副本重试、仅视频、不可播放。每种状态有短文本和正确的可重试操作。
- 非全屏：横屏固定 16:9；竖屏可以随信息区的连续滚动从“剧场比例”收缩至 16:9，当前已实现该交互。全屏：控件点击显示/自动隐藏，返回操作始终优先于滑动切换。
- 线上状态与完整性检查只显示为辅助信息，不能阻塞本地播放；“暂无法核验”必须解释为网络/登录/接口无法确认，而不是视频已下架。
- 后台播放的开关应明确影响“离开播放页”和“任务移除”两种情形；通知媒体元数据（标题、UP、封面）需要完整，系统媒体控件才可辨识。

**性能与可靠性。**

- Media3 官方建议背景播放将 player 与 session 放在 `MediaSessionService` 中；当前架构符合。为媒体项补齐 `MediaMetadata`（title/artist/artwork），利用服务自动生成的媒体通知和系统控制。
- 当前“读文件头 + 首帧 Bitmap”只能解决视觉切换，不能保证目标项音视频缓冲。对于动态竖滑队列，Media3 的 `DefaultPreloadManager` 正是官方针对一维列表/轮播预加载的方案：n+1 可加载约 3 秒，n-1 1 秒，n±2 只选轨，远项只 prepare。它应与正式播放器由同一 Builder 创建以共享组件。迁移前需确认项目 Media3 版本支持并进行压测。
- 自定义 Shizuku `DataSource` 的随机读取应维持“请求长度、偏移、耗时、失败原因”统计。将现有 6 MiB 内存块缓存变为按设备 RAM 分档、可清空、切队列即淘汰；避免把多个相邻高清视频的首段同时占满内存。
- 如果临时副本是兼容性回退，必须原子写入（`.part` → rename）、可取消、带空间预检与过期清理；不要在播放器主线程等待整文件拷贝。
- 针对 1080p/4K、横竖屏、仅视频、Shizuku/直读/SAF、损坏/删除中共至少 12 个设备级回归场景。Media codec 可用性因设备而异，JVM 单测无法证明真实播放性能。

### 3.6 全屏上下滑切换

**现状。** 当前先对相邻 2 条预读，手势露出目标后放大预读，并用 `PlaybackFirstFrameExtractor` 在目标 t=0 抽帧。目标项提交前展示首帧，避免黑闪；当前项在 drag 阶段持续播放。

**产品设计。**

- 手势优先级：顶部/底部控制区、横向进度条、选集面板打开时不触发切换；只有视频内容区的主轴拖动触发。
- 中间态应为两个完整“页面”随手指同向移动：当前页保持活视频，目标页显示首帧/轻量 loading；松手按速度与距离共同决定提交或回弹。
- 第一次使用提示一次“上滑切换下一条”；队列首尾提供柔和回弹而非无反馈。

**性能与可靠性。**

- 动画偏移必须用 lambda `Modifier.offset { ... }` 或图层变换，避免每个拖动像素触发整个页面重组。Compose 官方也建议用 `derivedStateOf` 限制高频状态导致的重组。
- 保持单一 ExoPlayer：拖动期不要创建第二个播放器或播放第二路音频。首帧仅限相邻一项、Bitmap 下采样到屏幕所需尺寸，避免 OOM。
- 预加载需有“快速连滑”取消策略：手势目标变更立即取消旧 target 高优先级任务，仅保留最近目标；预读完成不代表立即创建/切换媒体项。
- 用 Macrobenchmark/Perfetto 测量持续 20 次切换的 p50/p95“手指松开到首帧”和 dropped frames，而不是凭感觉调整阈值。

### 3.7 MP4 转换与导出任务

**现状。** `VideoConverterService` 通过 `MediaExtractor` 读取视频/音频轨，用 `MediaMuxer` 无损重封装；`ConversionForegroundService` 管理后台任务与进度。导出库与源缓存记录关联，但源缺失后仍保留导出路径。

**产品设计。**

- 单项与批量任务使用同一个任务中心：排队、当前项、已完成/失败数、剩余估计、暂停/取消、失败重试；通知栏和应用内状态保持一致。
- 导出前显示覆盖策略（重名跳过/自动改名/覆盖）和所需空间；输出成功后应提供“播放、打开目录、分享（如未来允许）”。
- 无法重封装时明确是“轨道格式/文件损坏/空间不足/权限问题”，并保留诊断详情。

**性能与可靠性。**

- 维持单任务串行，避免多个 `MediaExtractor`/I/O 同时争抢并导致播放卡顿。若将来支持并行，最多在明确储存性能测试后允许 2 路。
- 以已处理 sample 时间戳 / 总时长计算进度，同时报告“正在准备/写入尾部/封装完成”；这避免用户看到长时间 0% 或 100%。
- 输出采用临时文件和原子 rename；校验 muxer 关闭成功、时长/大小非零后才写 `exportedPath`。
- 实现真正的 cooperative cancellation（目前 `cancelAll()` 为空），在 sample 循环检查取消标记，删除 `.part`；Foreground service 需确保进程被回收后任务状态可恢复为“中断，可重试”。

### 3.8 已导出 MP4 库与文件管理同步

**现状。** 已导出页支持搜索、筛选、排序、批量分类/删除、重命名与播放。`ExternalMediaSyncService` 回前台或手动刷新时比较 `File.isFile`、大小、mtime，清除失效导出路径或更新指纹。

**产品设计。**

- 在库中显式区分“源缓存仍在”“仅剩导出文件”“导出文件已丢失”；避免用户误把“仅导出”理解成错误。
- 文件外部更名无法可靠地仅凭路径发现：刷新后可在导出目录内扫描候选 MP4，并提供“重新关联”而不是直接当作陌生文件。
- 删除操作分两类：“从应用库移除记录”与“删除磁盘 MP4”，默认突出后者的不可恢复风险。

**性能与可靠性。**

- 当前逐条 `File` 询问适合几百条，数千条可改为一次目录枚举构建 `path → size/mtime` 映射，再在 Room 单事务内批更新。
- 在可行的导出目录上注册 `FileObserver`，前台时做 300–500 ms debounce 增量同步；回前台仍保留全量核对作为兜底。不同设备上 observer 可能丢事件，因此不能代替手动刷新。
- 用更强的轻量 fingerprint（大小、mtime、可选头尾各 64 KiB hash）识别“同路径内容被替换”；hash 仅在 mtime/size 可疑时计算，不能每次全库读取。

### 3.9 原视频状态与媒体完整性

**现状。** 线上状态按 avid 去重请求，状态分 `UNCHECKED/ONLINE/UNAVAILABLE/UNVERIFIABLE`，24 小时复核、失败 15 分钟重试。批量“刷新全部”当前逐 AV 顺序请求，单次连接超时 8 秒。完整性检查独立于线上状态。

**产品设计。**

- 状态文案必须区分：`在线`（页面接口可访问）、`不可访问`（明确返回不存在/下架类结果）、`暂无法核验`（网络、登录、风控、服务异常或未知响应）、`待核验`（还未请求）。这不是“缓存文件是否能播放”的判断。
- 在批量刷新中展示“已请求 AV 数 / 总 AV 数、在线/不可访问/待重试”；支持停止，避免用户以为卡死。
- 不应声称能通过 AV/CID 证明线上文件与本地缓存像素级一致。除非取得线上媒体的稳定内容 hash/版本标识并被授权使用，否则只能比较页面可达性与元数据，不能证明是否重投、加马赛克等画面修改。

**性能与可靠性。**

- 将顺序请求改为受限并发（建议 2–4）加速大库，同时设全局速率限制、指数退避、Retry-After 处理和可取消协程，避免 API 限流后把大量条目误写为不可访问。
- 保存 HTTP/业务 code、检查时间、失败类型；对同 AV 多 P 只写一次网络结果，再批量更新该组。当前“按 AV 分组”已经做到，需补进度与并发控制。
- 完整性检查改成分级：快速 `stat` → 必要时 MediaExtractor headers → 用户明确点击才做深度读；滚动卡片不应自动做完整字节校验。

### 3.10 设置、可访问性、视觉与运维

**现状。** 设置页已有语言、全量状态刷新、MP4 输出路径、后台播放。全局已有深色主题、玻璃效果、骨架屏、空状态与底部导航。

**产品设计。**

- 设置补充“缓存与网络”页：封面缓存占用/清理、预读档位、仅 Wi‑Fi（若未来有网络功能）、状态刷新间隔、诊断导出。
- 玻璃效果只用于背景与少量容器；播放器控制层遵循正常媒体 UI 的低干扰原则（无重叠阴影/厚边框），触控目标至少 48 dp、文字使用系统可读字体而不是装饰字体。
- 支持 TalkBack：所有图标有描述，状态颜色之外带文字/图标，批量进度和错误通过 live region 宣告；中英文本不得硬编码在 Composable。
- 建立“诊断”页：版本、设备/API、Shizuku 连接、当前访问路径、最近扫描/转换/播放错误，可一键复制但不包含视频文件与敏感路径。

**性能与可靠性。**

- 重度模糊/blur 仅用在静态背景，滚动列表卡片不做实时模糊；动画限制在 alpha/translation，尊重系统减少动态效果设置。
- 建立 release 真机性能门槛，而不是用 debug 体验判断。Android 官方指出 Lazy list 的可靠性能测量应在 release/R8 优化版本进行，并推荐 Macrobenchmark 对启动、滚动、动画等真实流程采样。
- 加入 app 专属 Baseline Profile，覆盖冷启动、首页滚动、打开播放器、首次播放、扫描页。官方说明它能避免关键 Compose 路径在首次使用时依赖 JIT，并建议用 Macrobenchmark 验证收益。

## 5. 测量方案（先测再改）

1. **建立基准数据。** 准备 500、3,000、10,000 条 Room fixture；准备直读和 Shizuku 两类缓存目录、横竖屏与有/无封面样本。
2. **宏基准关键路径。** 冷启动首页、连续滚动 10 屏、输入搜索、切换列表/宫格、进入/退出播放器、连续 20 次上下滑、启动一次转换。记录 TTID、frame timing、p50/p95 操作时延、CPU、RSS、I/O 与 Binder 调用数。
3. **数据库观测。** 对所有首页/分类/搜索 SQL 执行 `EXPLAIN QUERY PLAN`；检查索引是否被使用，尤其是 sourceAvailable + 排序与 category 场景。
4. **失败注入。** 扫描中撤销 Shizuku、删除一个 m4s、删除封面、导出中空间不足、播放中删除源文件、线上状态网络超时。每一例验证用户文案、数据库最终状态、是否可重试。
5. **门槛。** 以当前 release 版本作为基线；任何优化必须同时给出指标改善或至少不回退，不能只根据 debug 手感合入。
